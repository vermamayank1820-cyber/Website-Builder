# 004 — Security & Access Document (SAD)

## 1. Authentication model

Supabase Auth is the sole identity provider (Google OAuth + email/password).
Credentials and password hashing are owned by Supabase — **the app stores no
passwords**. `auth.users` is the canonical user; `public.profiles` mirrors it
via the `handle_new_user` trigger. Sessions are JWTs stored in cookies;
`proxy.ts` refreshes them on every matched request.

## 2. Authorization model

**Row Level Security on every table**, owner-scoped via `auth.uid() = user_id`
(or an `exists` join to the owning row, e.g. `project_versions` → `projects`).
The anon/browser client can only ever read/write the signed-in user's rows. The
service-role client (`lib/supabase/admin.ts`) bypasses RLS and is **server-only**
(seeding / Auth admin) — it must never be imported into client code.

## 3. Roles & permissions

| Actor | Key | Access |
| --- | --- | --- |
| Anonymous | — | public routes only; protected routes redirect to `/login` |
| Authenticated user | anon key + session | own rows only (RLS) |
| Server (privileged) | service role | full (seeding, Auth admin); never exposed to browser |

There is no in-app role hierarchy (no admin/staff roles) today.

## 4. Session handling

`@supabase/ssr` cookie sessions; `proxy.ts` (Next middleware) refreshes the
session and enforces boundaries: unauthenticated → `/login` (with `next`);
authenticated on `/login` → `/workspace`. Guarded prefixes: `/workspace`,
`/project`, `/settings`, `/new`.

## 5. Secrets management

All secrets via environment variables — never hardcoded, never committed.
`OPENAI_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY` are server-only.
`NEXT_PUBLIC_SUPABASE_URL` / `_ANON_KEY` are public by design (RLS protects
data). `.env.local` is git-ignored; `.env.example` documents required keys.

## 6. Environment variables

| Var | Scope | Purpose |
| --- | --- | --- |
| `OPENAI_API_KEY` | server | LLM/vision |
| `OPENAI_MODEL` / `OPENAI_CODEGEN_MODEL` / `OPENAI_VISION_MODEL` | server | model routing |
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public | auth + RLS-scoped data |
| `SUPABASE_SERVICE_ROLE_KEY` | server | seeding / Auth admin only |

## 7. Input validation

- Zod at every API boundary (`lib/ai/schema.ts`, route schemas).
- Size limits: user text `min 3` / `max 200,000`; files ≤ 25MB, allowed
  extensions only.
- DB `CHECK` constraints enforce enum values (status, category).
- Generated code is parsed/repaired before storage/render.

## 8. Database security

RLS-by-default; FK `on delete cascade`; parameterized queries only (supabase-js
— no string-built SQL anywhere). The `generations` table is owner-scoped; the
service role is the only path that bypasses RLS, and only server-side.

**Artifact storage (platform, future surfaces):** binary artifacts (image /
video / audio) generated by v2+ surfaces go to **Supabase Storage** buckets that
must be **private and owner-scoped** (signed URLs only; never a public bucket
for user content). The `thumbnails` bucket is public by design (non-sensitive
previews) and is the only exception. Sharing links must be capability-scoped
(unguessable, optionally expiring), not "public bucket".

## 9. API security

- Server-only secrets; consistent error envelope without leaking internals.
- `ProviderError` carries a safe HTTP status; stack details stay server-side.
- Generated/untrusted code runs in a **sandboxed iframe** (`allow-scripts`,
  no same-origin) — it cannot touch the app session or DOM.
- Document parsing/OCR run server-side on validated, size-capped uploads.

## 10. Rate limiting

**Not implemented.** Per-user/IP rate limiting on `/api/generate`, `/api/parse`,
`/api/ocr`, `/api/understand` (all LLM- or compute-heavy) is an open risk — see
§13 and FTL `SEC-01`.

## 11. Audit logging

`agent_runs` logs Business-OS activity; `[DocumentParser]` logs parse/OCR
outcomes. There is **no centralized security audit log** (auth events, data
access) — open item (FTL `SEC-02`).

## 12. Content Security Policy / headers

Production CSP and security headers (HSTS, X-Content-Type-Options, frame
controls) are **not yet configured** — recommended before public launch.

## 13. Security assumptions & risks

- **Assumed:** Supabase RLS correctly scopes all reads/writes; service-role key
  never reaches the client; the preview iframe stays sandboxed.
- **Risks / open items:** no rate limiting (cost/DoS exposure on LLM routes);
  no CSP/security headers; no audit log; OCR/parse accept untrusted binaries
  (mitigated by size caps + server isolation, but worth sandboxing further);
  generated code is third-party-ish content (mitigated by iframe sandbox).
